                   Chapter 1: Introduction
 Modular, Updateable Filesystem for Bare Metal as a Service (ModFS)




1    Context and Motivation
In modern cloud infrastructure, edge environments, and Bare Metal as a Service (BAAS) plat-
forms, rapid, predictable, and storage-efficient server provisioning is a core operational require-
ment. BAAS platforms automate the lifecycle of physical servers, provisioning raw hardware
nodes with operating system images on demand. Unlike virtualized multi-tenant environments
where hypervisors or container runtimes isolate workloads on shared hosts, bare-metal deploy-
ment requires flashing full root filesystem images directly onto host storage media or serving
them over network-attached block devices.
     Historically, BAAS image management has relied on monolithic, whole-disk binary blobs. In
this paradigm, every operating system configuration, application stack, or tenant environment
is built, compressed, and stored as an independent, opaque disk image. When multiple server
workloads share a common operating system baseline—such as an Ubuntu 22.04 LTS (Jammy
Jellyfish) installation running on the x86-64 architecture with APT/dpkg package management—
this monolithic model introduces massive storage redundancy. For example, maintaining ten
distinct server configurations (e.g., dedicated web servers, database nodes, build runners, and
machine learning hosts) that all build upon the same underlying Ubuntu operating system
baseline requires storing ten complete, redundant operating system copies on the provisioning
server.
     Furthermore, software updates and security patching in monolithic BAAS pipelines suffer
from severe inefficiency. Updating a single low-level library (such as libssl or glibc) or a
single application package requires completely rebuilding, re-indexing, and re-shipping every
full disk image across the provisioning network. This whole-image operational pattern drives up
server-side storage costs, increases network bandwidth consumption during node deployment,
and introduces substantial deployment latency.
     While containerization technologies (e.g., Docker) and virtual machine template pools mit-
igate redundancy in virtualized environments through image layering, bare-metal provisioning
demands a native, high-performance filesystem layout that boots directly on host hardware
under standard Linux systemd initialization while preserving fine-grained modularity and up-
dateability.


2    Problem Statement
Existing image management solutions in Bare Metal as a Service lack modular granularity and
fine-grained update mechanisms. Storing monolithic whole-disk images results in storage bloat
that scales linearly with the number of provisioned use cases (N × B, where B is the baseline
image size and N is the number of workloads).
    Naively attempting to compose modular filesystem deltas at runtime or build time by overlay-
ing independently compiled package sets introduces severe filesystem-level and package-level
state conflicts:

    1. Uncontrolled Dependency Drift and Version Skew: Installing packages into indepen-
       dent module layers at different times against dynamic distribution repositories causes

       package version skews, broken inter-module dependency chains, and implicit base oper-
       ating system upgrades, destroying deployment predictability.

    2. File Path Collisions: Independent module builds can overwrite overlapping file paths
       or place conflicting binaries in shared FHS (Filesystem Hierarchy Standard) paths (e.g.,
       /usr/bin, /etc), leading to file loss or layer-order-dependent binary execution.
    3. State Divergence in Shared Registries: Multiple package installations modify shared,
       unowned system registries—global system databases that record installation state, user
       accounts, and system configuration. Key examples include:

          • The package status database (/var/lib/dpkg/status).
          • Configuration database records (debconf config.dat and templates.dat).
          • System account databases (/etc/passwd, /etc/group, /etc/shadow, /etc/gshadow,
            /etc/subuid, /etc/subgid).
          • The alternative symlink registry (/var/lib/dpkg/alternatives/* and /etc/alternatives/*).
          • The dynamic linker binary cache (/etc/ld.so.cache).
          • The package diversion database (/var/lib/dpkg/diversions).
          • Extended package auto-installation states (/var/lib/apt/extended_states).

       Overlaying these files naively using standard union filesystems causes the topmost layer
       to overwrite lower layers, rendering lower-layer packages invisible to package manage-
       ment tools or breaking system services.

    4. Numeric Identity Collisions: Independent maintainer scripts allocate numeric User IDs
       (UIDs) and Group IDs (GIDs) dynamically at build time (e.g., adduser system). Two
       independent modules can allocate the exact same numeric UID/GID (e.g., UID 103) to
       different service account names (e.g., redis vs. memcache), causing severe security and
       permission corruption when stacked.

    5. Directory Erasure via Opaque Markers: Standard union filesystems (OverlayFS) write
       extended attributes (trusted.overlay.opaque) when directories are recreated during
       package builds. Stacking deltas containing these opaque markers causes upper lay-
       ers to silently erase directory contents originating from lower layers without generating a
       direct file path collision.

    6. Runtime Resource Races: Even when package sets compose cleanly at the filesystem
       layer without metadata conflicts, runtime services can collide over unmanaged physical
       hardware resources (such as two web servers, nginx and apache2, competing to bind to
       port 80).


3     Strategy and Proposed Solution: ModFS
To solve these challenges, this thesis presents ModFS, a modular, updateable filesystem
framework engineered specifically for Bare Metal as a Service. ModFS replaces opaque whole-
disk binary blobs with thin, composable module deltas built upon a shared, immutable base
operating system image.
    The core design of ModFS rests on four key architectural principles:

    1. Archive Pinning: Every build in the system draws from a single, fixed archive repository
       snapshot (snapshot.ubuntu.com/ubuntu/<TIMESTAMP>), freezing all package versions
       and dependency resolution to an exact point in time.

Chapter 1: Introduction                                                                ModFS Thesis


    2. Base and Pinned Sibling Deltas: A single base system image is constructed using
       debootstrap and fully upgraded against the pinned snapshot. Thin per-use-case mod-
       ules are created by mounting the parent base read-only as a lower layer in OverlayFS,
       installing target packages into the merged view, and squashing only the upper directory
       (upperdir) into a compressed SquashFS archive (.sqsh).

    3. Semantic State Reconciliation: To compose a bootable image, sibling modules are
       stacked as read-only lower layers alongside a dynamically computed reconciliation
       layer placed on top. This reconciler executes record-level union functions over diverged
       system registries (dpkg status, debconf, passwd, group, shadow, gshadow, subuid, subgid,
       extended_states, diversions) and regenerates tool-owned derived state (ld.so.cache,
       /etc/alternatives/*).
    4. Multi-Tier Evaluation Framework: To ensure that a composed set of modules forms a
       valid, bootable system prior to bare-metal node flashing, ModFS implements a three-tier
       validation pipeline:

          • Tier 1 (Static Metadata Admission): Fast, rootless evaluation over declarative
            module manifests (module.json) to verify dependency closure and detect conflict
            classes.
          • Tier 2 (Structural & Registry Verification): Physical layer composition and verifica-
            tion of exact registry record unions, symlink target integrity, and file visibility across
            stacked layers.
          • Tier 3 (QEMU UEFI Boot Testing): Automated virtual machine boots under UEFI
            and systemd to verify service startup and detect runtime resource collisions.


4    Central Claim and Research Questions
The central thesis claim of this work is that archive snapshot pinning reduces an other-
wise intractable file-level conflict problem into a small, declarative, package-level verifi-
cation problem.
   To systematically validate this central claim, this thesis investigates three primary Research
Questions (RQs):

     • RQ1 (Conflict Taxonomy & Reconciliation): How can file-level and package-level state
       conflicts across independent filesystem deltas be systematically classified, prevented,
       and reconciled?

     • RQ2 (Storage Efficiency): What server-side storage savings does the pinned sibling
       delta model achieve compared to traditional monolithic disk images across diverse work-
       load scales?

     • RQ3 (Verification & Boot Reliability): How effectively can static metadata admission
       and structural verification predict the bootability and runtime service health of composed
       modular systems?

straints:

     • Target Operating Environment: Ubuntu 22.04 LTS (Jammy Jellyfish), APT/dpkg pack-
       age management, and x86-64 processor architecture.

2 System Background and Linux Primitives
Modern Linux distributions provide software modularity through package management systems
and kernel-level lesystem abstractions.      ModFS targets the   Ubuntu 22.04 LTS (Jammy
Jellysh) distribution operating on the x86-64 architecture under the standard APT and dpkg
software management toolchain.


2.1 Package Management Mechanics and Maintainer Scripts
In Debian-derived Linux distributions, software lifecycle management is split between low-level
archive execution (dpkg) and high-level dependency resolution (APT). Packages are delivered as
compressed binary archives (.deb) containing compiled executables, shared libraries, congura-
tion les, control metadata, and executable shell scripts known as   maintainer scripts (preinst,
postinst, prerm, postrm).
   When APT installs a set of requested packages, the installation proceeds through four distinct
operational phases:


     1.   Dependency Resolution and Order Calculation: APT parses repository Packages
          indices, resolves disjunctive dependencies, and computes a topologically sorted execution
          plan.




                                                   3
  2.   Archive Extraction and Direct File Unpacking: dpkg extracts the payload tarball of
       each package directly into the target lesystem root (/). Every unpacked le is registered
       in the package's ownership manifest (/var/lib/dpkg/info/<package>.list).


  3.   Maintainer Script Execution: dpkg executes maintainer scripts (preinst before un-
       packing payload, postinst after unpacking payload). Maintainer scripts perform arbitrary
       imperative operations, such as creating system users via adduser, registering congura-
       tion templates via debconf, updating symlinks via update-alternatives, and populating
       database schemas.


  4.   Trigger Processing and Deferred Hooks: dpkg runs registered trigger routines to
       update global caches (e.g., invoking ldconfig to rebuild shared library search structures
       or update-initramfs to build boot ramdisks).


2.2 The Seven Unowned System Registries
A fundamental challenge in modular lesystem composition is that package installations modify
two distinct categories of state:   owned les and unowned system registries. Owned les belong
explicitly to a single package (e.g.,   /usr/bin/nginx) and are tracked in its .list manifest.
Unowned system registries, in contrast, are global database les that are not owned by any
individual package but are mutated dynamically by multiple packages during maintainer script
execution.
   ModFS identies seven critical system registries that inevitably diverge when packages are
installed into separate lesystem deltas:


2.2.1 1. Package Status Database (/var/lib/dpkg/status)
The dpkg status database is a plain-text le formatted as a sequence of RFC-822-style stanzas.
Each stanza records the authoritative state of a single package on the host:


Package: nginx-core
Status: install ok installed
Priority: optional
Section: httpd
Installed-Size: 1478
Maintainer: Ubuntu Developers <ubuntu-devel-discuss@lists.ubuntu.com>
Architecture: amd64
Version: 1.18.0-6ubuntu14.4
Depends: libc6 (>= 2.34), libpcre3, zlib1g (>= 1:1.1.4)
Provides: httpd, httpd-cgi
Description: nginx core binary...
When two independent module deltas install packages on top of the same base system, each
delta modies its local /var/lib/dpkg/status le. Stacking these deltas in a standard union
lesystem causes the upper layer's status le to completely overwrite the lower layer's status
le. As a result, all packages installed in the lower layer become invisible to dpkg, rendering the
system unmaintainable and breaking dependency checking.


2.2.2 2. Conguration Database (debconf / config.dat, templates.dat)
The Debian conguration management system (debconf) maintains two binary/text backend
les under /var/cache/debconf/: config.dat (which stores user conguration selections, ques-
tion ags, and variable bindings) and templates.dat (which denes the schema and interna-
tionalized prompts for package queries). Maintainer scripts query and update debconf during



                                                 4
installation via the    debconf-communicate protocol.   Independent package installations alter
these databases, causing last-writer-wins overwrite conicts when stacked.


2.2.3 3. User and Group Account Databases (/etc/passwd, /etc/group, /etc/shadow,
      /etc/gshadow, /etc/subuid, /etc/subgid)
POSIX identity management relies on at text databases mapping account names to numeric
identiers (UIDs and GIDs):

    /etc/passwd: Maps usernames to numeric UIDs, primary GIDs, home directories, and
      default shells.

    /etc/group: Maps group names to numeric GIDs and user membership lists.
    /etc/shadow & /etc/gshadow: Store encrypted password hashes, expiration dates, and
      administrative ags.

    /etc/subuid & /etc/subgid: Subordinate UID/GID ranges allocated for unprivileged
      user namespace container execution.

Package maintainer scripts frequently create system accounts dynamically using commands such
as adduser   system group home /var/lib/redis redis. When system accounts are allo-
cated dynamically across independent module builds without coordination, two independent
modules can allocate the exact same numeric UID (e.g., UID 105) to entirely dierent service ac-
counts (e.g., redis in Module A vs. postgres in Module B), leading to critical security breaches
and le permission corruption.


2.2.4 4. Extended Package States (/var/lib/apt/extended_states)
APT maintains an explicit record of whether each installed package was manually requested by
the system administrator or automatically pulled in as a transitive dependency:

Package: libpcre3
Auto-Installed: 1

Package: nginx
Auto-Installed: 0
This state governs automatic package pruning (apt-get      autoremove).      Independent module
installations append stanzas to extended_states, requiring record-level merging during compo-
sition.


2.2.5 5. Alternative Symlink Registry (/var/lib/dpkg/alternatives/* and /etc/alternatives/*)
Debian manages default command selection (e.g., choosing which binary fullls /usr/bin/editor
or /usr/bin/java) through update-alternatives. The authority database under /var/lib/dpkg/alternative
records priority scores, slave links, and available provider paths. The corresponding symlinks
in /etc/alternatives/ point to the highest-priority registered provider. Independent package
installations append alternative choices, requiring both database record merging and dynamic
symlink recalculation.


2.2.6 6. File Diversion Registry (/var/lib/dpkg/diversions)
When a package must overwrite a le belonging to another package,        dpkg-divert instructs
dpkg to write the original le to a diverted location (e.g., /usr/bin/gcc.real). The registry at
/var/lib/dpkg/diversions tracks all active redirections. Divergent diversions across modules
must be unied to prevent package le collisions.

2.2.7 7. Dynamic Linker Cache (/etc/ld.so.cache)

2.3 OverlayFS Mechanics and Mutation Capture
Linux OverlayFS is an in-kernel union lesystem that presents a single merged directory tree
derived from multiple underlying directories (branches).     An OverlayFS mount requires four
physical directory paths:

  mount -t overlay overlay -o lowerdir = L1 : L2 : · · · : Ln , upperdir = U, workdir = W   M    (1)

where L1 . . . Ln are read-only lower directories, U is a read-write upper directory, W is a dedi-
cated work directory on the same lesystem as U , and M is the target merged mount point.
   OverlayFS intercepts Virtual Filesystem (VFS) operations and handles state modications
according to three primary semantics:

    Copy-On-Write (COW): When an application opens a lower-layer le for writing, Over-
     layFS copies the complete le from the read-only lowerdir to the writable upperdir be-
        fore executing the modication. File permissions, timestamps, owner UIDs, and extended
        attributes are preserved during copy-up.

    Whiteouts (c 0 0):        When an application deletes a le originating from a read-only
        lower layer, OverlayFS creates a special   whiteout character device node in upperdir
        with major device number 0 and minor device number 0. During path lookup (lookup())
        and directory enumeration (readdir()), the kernel recognizes whiteout nodes and hides
        the corresponding lower-layer le from user space.

    Opaque Directories (trusted.overlay.opaque = "y"): When a directory existing in
        a read-only lower layer is deleted and subsequently re-created in the merged view (e.g.,
        executing rm  -rf /etc/conf.d && mkdir /etc/conf.d), OverlayFS creates the new di-
        rectory in upperdir and attaches an extended attribute trusted.overlay.opaque = "y".
        When looking up paths inside an opaque directory, the OverlayFS kernel driver stops scan-
        ning any lower layers, preventing lower-layer directory contents from appearing inside the
        newly created directory.


2.4 Immutable Compressed Storage via SquashFS
SquashFS is a read-only, block-compressed lesystem driver built into the Linux kernel. SquashFS
packages entire directory hierarchies, regular les, symbolic links, character/block device nodes,
FIFOs, sockets, and extended attributes into a dense, contiguous binary image (.sqsh).
   ModFS utilizes SquashFS to encapsulate OverlayFS upper directories into portable, read-
only module archives.     SquashFS is uniquely suited for delta storage due to three technical
characteristics:

   1.   Device Node and Xattr Preservation: SquashFS natively preserves character device
        nodesincluding major/minor 0:0 OverlayFS whiteout devicesand extended attributes
        (such as trusted.overlay.opaque).

   2.   High Compression Ratios: Utilizing modern block compression algorithms (zstd with
        128 KB or 1 MB block sizes), SquashFS achieves 60% to 75% storage compression compared
        to raw uncompressed tarballs or ext4 images.



                                                   6
  3.   Direct Kernel Mountability: SquashFS archives can be mounted directly by the Linux
       kernel via loop devices without requiring prior decompression or extraction to temporary
       disk storage.



3 Namespace Unication and Layered Filesystems
The concept of unifying independent directory trees into a single, cohesive namespace has a rich
history in operating system research. This section examines foundational stackable lesystems
and contrasts their runtime lookup interception models against ModFS's static delta squashing
architecture.


3.1 Foundational Stackable and Union Filesystems
3.1.1 4.4BSD Union Mounts (Pendry & McKusick 1995)
Pendry and McKusick [1] introduced in-kernel union mounts in 4.4BSD-Lite.              Their design
allows directory hierarchies to be mounted transparently over existing directories using VFS
vnode stacking.


       Whenever a whiteout is replaced by a directory, the directory inode is automatically
       tagged with the opaque attribute...   During a lookup in a union stack, the union
       lesystem does not continue to the lower layer object if the upper layer object is
       marked opaque. To understand this requirement, consider the sequence of operations:
       rm -rf tree, mkdir tree... By marking the newly created upper layer directory
       with the opaque attribute the union lesystem ensures that the semantics prevents
       the lower layer objects in tree from becoming visible.      Pendry & McKusick [1],
       Section 5.1


   The 4.4BSD union mount mechanism established two core primitives used in modern union
lesystems:


    Layered Priority: Lookup requests scan layers from top to bottom, returning the rst
       matching le name.


    Opaque Directories and Whiteouts: File deletion in read-only lower layers is recorded
     by creating explicit whiteout directory entries (DT_WHT) in the upper layer, while newly
     created directories that replace deleted trees are marked with an opaque ag to stop lower-
       layer lookup continuation.


3.1.2 Unionfs (Wright et al. 2006)
Wright et al. [2] presented Unionfs, an n-way fan-out stackable lesystem for Linux operating
directly over arbitrary VFS physical branches.


       Unionfs is a stackable le system that operates on multiple underlying le systems.
       It has an n-way fan-out architecture... In this example, the branches are a read-write
       Ext2 le system, a read-only Ext2 le system, a read-write NFS le system, and a
       read-only ISO9660 le system.                             Wright et al. [2], Section 2


   Unionfs introduced dynamic branch management (allowing branches to be inserted, removed,
or re-ordered at runtime) and complex copy-up handling across mixed read-write and read-only
storage media. However, Unionfs operates strictly at runtime via live VFS call interception: all
lookups, directory enumerations (readdir), and duplicate suppression algorithms run inside the

4 Formal Package Co-Installability and Dependency Solvers
A central domain of research in software engineering is formal package repository analysis. This
section reviews declarative dependency solvers and contrasts their metadata models with physical
lesystem state reconciliation.


4.1 Declarative Repository Models and SAT Encodings
The EDOS (Evolution and Quality of Open Source Software) and Mancoosi projects formalized
package repository co-installability using mathematical logic [5, 6, 7].
   A package repository is formally dened as a tuple:

                                          R = (P, D, C)                                         (2)

whereP is a nite set of package identiers, D : P → P(P(P )) is a dependency function
mapping each package to a set of dependency disjunctions, and C ⊆ P × P is a symmetric,
irreexive declared conict relation.


4.1.1 NP-Completeness and SAT Solvers
Mancinelli et al.   [6] and Treinen & Zacchiroli [5] proved that determining whether a set of
packages can be co-installed under repository dependencies D and conicts C is NP-complete
by reduction from 3-SAT.
   To verify repository consistency, tools like edos-debcheck convert package metadata into
Conjunctive Normal Form (CNF) boolean formulas:

    If package A depends on B ∨ C , it generates the clause: ¬A ∨ B ∨ C .
    If package A conicts with B , it generates the clause: ¬A ∨ ¬B .
High-performance SAT solvers (such as pkglab) then evaluate whether a satisfying truth assign-
ment exists for target package installations.


4.1.2 Certied Co-installability Kernels (coinst)
Vouillon and Di Cosmo [7] developed coinst, a formally certied graph reduction framework
that extracts minimal co-installability kernels from vast package repositories.

     A repository is a tuple R = (P, D, C) where P is a nite set of packages, D : P →
     P(P(P )) is the dependency function... and C , a symmetric irreexive relation over
     P , is the conict relation.               Vouillon & Di Cosmo [7], Section 2.1


4.2 The Critical Gap: Metadata Solvers vs. Physical File System State
While SAT-based metadata solvers rigorously verify declarative package dependencies (D ) and
explicit conict declarations (C ), they possess a critical limitation:    they operate entirely
outside physical lesystem reality.
   As Vouillon & Di Cosmo [7] explicitly state in their formal model, packages are treated as
opaque atomic nodes p ∈ P . The formal model contains no representation of on-disk le paths,
directory structures, maintaining script execution, or system registries.
   Treinen & Zacchiroli [5] recognized this limitation and introduced a static le collision check:

     A rst idea towards a better solution is to only consider those pairs of packages
     that actually share at least one le. Luckily, the information which package contains
     which le is available in the le Contents of the distribution... Co-installability is
     checked with the pkglab tool... This rst phase gives us a reduced list of pairs of
     packages.                                      Treinen & Zacchiroli [5], Section 2.2.5

sions. It cannot detect:


   1.   State Divergence in Unowned Registries: Two packages that do not share any owned

1 High-Level Architecture and Core Design Pillars
ModFS is a modular, updateable lesystem architecture engineered specically for Bare Metal
as a Service (BAAS) infrastructure. Traditional BAAS image pipelines treat operating system
environments as monolithic, opaque whole-disk binary blobs. When multiple distinct server
workloads share a common operating system foundation (such as an Ubuntu LTS release), this
monolithic model requires storing, versioning, and distributing full-disk images for every work-
load variant. For instance, provisioning ten distinct application environments that all build upon
the same base operating system results in ten redundant full-disk copies on the server repository.
Furthermore, updating or patching a single software package requires rebuilding, re-indexing,
and re-shipping every full disk image across the network.
    ModFS replaces opaque whole-disk blobs with thin, composable module deltas built upon
a shared base operating system image. Rather than attempting to compose lesystems dynam-
ically at runtime on host nodes or relying on ad-hoc package overlays, ModFS introduces a
server-side build, verication, and composition pipeline that operates on four core architectural
pillars:

+-----------------------------------------------------------------------------------+

                                      v

1. Archive Snapshot Pinning: Every build in the system draws package repositories from
   a single, xed archive snapshot (snapshot.ubuntu.com/ubuntu/<TIMESTAMP>). The times-
   tamp identier is explicitly embedded in the repository URL path. This freezes package ver-
   sion resolution across the entire distribution archive (main, restricted, universe, multiverse,
   jammy-updates, and jammy-security), ensuring that dependency solvers operate over a com-
   pletely static package graph.
2. Base and Pinned Sibling Deltas: A single base system image (base.sqsh) is constructed
   using debootstrap and fully upgraded (apt-get full-upgrade) against the pinned archive
   snapshot. Thin per-use-case modules are created by mounting the base image read-only as
   a lower layer in OverlayFS, installing requested target packages into the merged view, and
   squashing only the upper directory (upperdir) into a compressed SquashFS archive (.sqsh).
   Because APT sees the base system as already installed, the upperdir captures only newly
   created or modied les. The lesystem captures the di implicitly; ModFS never computes
   le dis manually.

3. Semantic State Reconciliation: To compose a bootable OS image for a specic server
   workload, a set of module deltas is stacked as read-only lower layers alongside a dynamically
   computed reconciliation layer placed on top. This reconciler performs semantic record-
   level unions over diverged system registries that are rewritten by maintainer scripts but
   owned by no single packageincluding dpkg status stanzas, debconf conguration databases,
   user and group account records (passwd, group, shadow, gshadow, subuid, subgid), le
   diversions, and extended package states. Derived binary caches (such as /etc/ld.so.cache
   and /etc/alternatives/* symlinks) are recomputed inside the merged view using their
   native owning tools (ldconfig, update-alternatives).

4. Multi-Tier Evaluation Framework: Before ashing a composed image onto bare-metal
   hardware, ModFS executes a three-tier validation pipeline. Tier 1 performs rapid, rootless
   static metadata admission over module manifests to verify dependency closure and detect
   conict classes. Tier 2 mounts physical SquashFS deltas, executes registry reconciliation,
   and veries structural le visibility, symlink target validity, and registry completeness. Tier 3
   packs a attened UEFI image, boots it under QEMU, and executes automated service probes
   under systemd to detect runtime resource races.

1.1 Architectural Constraints
To maintain strict determinism and prevent combinatorial state explosion, ModFS enforces
explicit architectural boundaries:

 Flat Sibling Topology: All module deltas exist as direct pinned siblings built against the
  base image. Delta-on-delta nesting (building a module on top of another module) is strictly
  prohibited.

 Atomic Generation Moves: An archive snapshot timestamp denes an immutable gen-
  eration. Moving the archive pin requires rebuilding the base image and all sibling modules
  atomically into a separate generation root (MODFS_ROOT). Mixing deltas across dierent gen-
  erations or snapshots is explicitly forbidden.

 Server-Side Image Flattening: ModFS composes, reconciles, and attens module deltas
  into an ext4 root lesystem image on the build server. The provisioned bare-metal node
  receives a standard, attened disk image. ModFS does not perform on-node runtime module
  switching or live rollback.

 2.2 Deterministic Delta Build Mechanics
 Achieving bit-for-bit reproducible SquashFS deltas across repeated builds required isolating four
 distinct sources of build non-determinism:

  Superblock and Inode Timestamps: mksquashfs by default embeds the build wall-clock
   time into the superblock and preserves le modication times. ModFS passes -mkfs-time
   <TIMESTAMP> and -all-time <TIMESTAMP> derived from the snapshot timestamp (SOURCE_DATE_EPOCH).
  Transient Build Logs: Package installation generates transient build logs containing execu-
   tion timestamps (/var/log/dpkg.log, /var/log/apt/history.log, /var/log/apt/term.log,
   /var/log/apt/eipp.log.xz, /var/log/alternatives.log, /var/log/bootstrap.log). These
   paths are excluded during squashing via SQUASH_EXCLUDES.

  OverlayFS Bookkeeping Extended Attributes: Mounting an OverlayFS upperdir gen-
   erates random kernel UUIDs and origin tracking attributes. ModFS passes -xattrs-exclude
   trusted.overlay.uuid and -xattrs-exclude trusted.overlay.origin to mksquashfs.
  Random Host Machine Identiers: systemd generates a random 128-bit machine ID
   in /etc/machine-id during package installation. ModFS empties /etc/machine-id before
   squashing, allowing systemd to regenerate a fresh ID upon rst boot on bare metal.

3 The 9-Class Conict Taxonomy and Policy Engine
When independent module deltas are built against a shared base image and subsequently com-
posed, lesystem- and package-level state collisions inevitably arise. ModFS establishes a com-
prehensive 9-Class Conict Taxonomy that classies every form of inter-module divergence,
dening explicit detection methods and enforced resolution policies for each.

| # | Conflict Class | Root Cause | Detection Method | Enforced Policy |
+----+---------------------------+---------------------------------+---------------------------------

| 1 | Benign Overlap | Same package & version in deltas| Version equality in stanza
    union | ACCEPT (measure duplication) |
| 2 | Version Skew | Mismatched snapshots / pins | Compare generation & versions |
    REJECT |
| 3 | Declared Conflict | dpkg Conflicts: / Breaks: | Match relations vs virtual names
     | REJECT |
| 4 | File Collision | Unrelated packages share path | Intersect .files.json.zst
    sidecars| REJECT (honor Replaces/Diversions) |
| 5 | State Divergence | Shared unowned registry edit | Structural, always occurs |
    RECONCILE / REGENERATE |
| 6 | Implicit Base Upgrade | Delta upgrades base package | Compare delta vs parent

| 7 | Identity Collision | Overlapping UID/GID allocation | Compare account records &
    file IDs| PREVENT (UID range partitioning) |
| 8 | Runtime Resource Conflict | Services compete for socket/port| Observable only at

| 9 | Opaque Directory Erasure | trusted.overlay.opaque xattr | Inventory xattrs
    across deltas | PREVENT (strip xattr at squash) |

3.1 Detailed Breakdown of Conict Classes
1. Class 1: Benign Overlap: Two sibling modules independently install the exact same De-
   bian package at the identical version (e.g., both git and pytools pulling in ca-certificates=20211016).
   During stanza union in reconcile.py, package names and version strings match bit-for-bit.
   Enforced policy: ACCEPT. The reconciliation layer retains a single copy of the status stanza.
   ModFS logs the overlap to measure package duplication.

2. Class 2: Version Skew: Modules are built against dierent archive snapshots, dierent
   parent base images, or explicit package pin overrides, introducing conicting package versions
   (e.g., curl=7.81.0-1 in module A vs curl=7.74.0-1 in module B). Evaluated at Tier 1 by
   05_check.sh and at Tier 2 by verify_compose.py (V2 check), comparing (package_name,
   version) pairs across manifests. Enforced policy: REJECT.
3. Class 3: Declared Metadata Conict: Installed packages declare explicit mutual exclu-
   sion in their control metadata (Conflicts:, Breaks:). 05_check.sh parses raw dpkg relation
   strings, expanding and resolving virtual package providers (e.g., detecting that msmtp-mta
   and nullmailer both provide and conict over mail-transport-agent). Enforced policy:
   REJECT.
4. Class 4: File Path Collision: Two distinct, co-installed packages attempt to write dif-
   ferent les to the exact same physical path (e.g., two packages providing /usr/bin/tool).


                                               7
  05_check.sh intersects the compressed path sidecars (<module>.files.json.zst). Directo-
  ries are ltered out because standard FHS directories (/usr/bin, /usr/share) are shared by
  design. Enforced policy: REJECT. If a package explicitly declares Replaces: or registers a
  path diversion (dpkg-divert), the collision is recognized as legitimate, logged as suppressed,
  and accepted.

5. Class 5: System Registry Divergence: Multiple package maintainer scripts modify
   shared, unowned system registry les during installation. Structural and universal. Every
   module that installs software alters /var/lib/dpkg/status and /var/lib/apt/extended_states.
   Enforced policy: RECONCILE or REGENERATE. Handled by reconcile.py and in-
   chroot tool execution.

6. Class 6: Implicit Base Upgrade (Base Drift): Installing a package into a module triggers
   APT to upgrade a transitive dependency that was already present in the read-only base image,
   creating a modied copy in the module's upperdir. 05_check.sh compares every package
   version in a delta against the parent base manifest (base.json). Enforced policy: PRE-
   VENT & REJECT. ModFS eliminates base drift by executing apt-get full-upgrade
   during the base build (01_build_base.sh).

7. Class 7: Numeric Identity Collision: Maintainer scripts in independent modules exe-
   cute adduser system or useradd -r, dynamically allocating identical numeric system UID-
   s/GIDs to completely dierent service accounts (e.g., redis receiving UID 103 in module A
   while memcached receives UID 103 in module B). 05_check.sh compares account database
   records across manifests and audits physical le ownership IDs (file_uids, file_gids) de-
   rived from the SquashFS upperdirs. Enforced policy: PREVENT & REJECT. Prevented
   at build time via append-only UID range partitioning.

8. Class 8: Runtime Resource Conict: Modules pass all static package and le checks,
   but their underlying background daemons compete for unmanaged host resources at runtime
   (e.g., webserver installing nginx and apache installing apache2, both attempting to bind
   to 0.0.0.0:80). Invisible to dpkg metadata and static lesystem checks. Detected exclu-
   sively at Tier 3 during QEMU UEFI boot testing when systemd reports a failed service unit
   (apache2.service failing with Address already in use). Enforced policy: OBSERVE.
   Documented as an intrinsic system boundary; no lower-tier static detection is possible.

9. Class 9: Opaque Directory Erasure: OverlayFS sets the extended attribute trusted.overlay.opaque
   = "y" when a directory is replaced during package build time. When stacked, this opaque
   marker instructs the kernel to hide all lower-layer les at that path, silently erasing les
   contributed by sibling modules without producing a le collision. Measured across the cata-
   logue upperdirs (869 markers across 456 distinct directories). Enforced policy: PREVENT.
   ModFS strips trusted.overlay.opaque extended attributes during SquashFS delta construc-
   tion (02_build_delta.sh). Tier 2 verication (V7 check) asserts that every path present in
   any layer remains visible in the merged view.

4 Append-Only UID/GID Range Partitioning
In Debian and Ubuntu systems, service accounts are created dynamically during package in-
stallation when maintainer scripts (postinst) execute adduser system or useradd -r. These
tools query current system allocation state and assign the next available numeric ID from the
system user pool (typically UID/GID range 100999).
    When building independent module deltas on top of a shared base, this dynamic allocation
produces severe numeric identity collisions. Because each module is built in isolation against
the clean base image, maintainer scripts across dierent modules assign the exact same numeric
UID (e.g., UID 103) to dierent service accounts:
  Naive Build (Colliding Allocations) ModFS Range Partitioning (Disjoint Windows)
  +-----------------------------------+ +-----------------------------------+
  | Module A (redis): redis=103 | | Module A (redis): redis=4600 | (Window 4600-4699)
  | Module B (memcached): memcache=103| | Module B (memcached): memcache=4700| (Window
       4700-4799)
  +-----------------------------------+ +-----------------------------------+
                  | |
                  v v
  OverlayFS Top-Layer Wins: Reconciled Identity Database:
  Numeric UID 103 reads as memcache! redis=4600, memcache=4700.
  redis-server fails to resolve User=redis. Both services resolve correctly!

    This failure cannot be repaired by simple database text merging: les on disk in the SquashFS
delta are stored using the numeric UID/GID in their inode metadata, not the string account
name. If numeric IDs collide, les owned by redis in module A read as owned by memcache in
a composition where module B sits on top.

4.2 Account Audit and Database Reconciliation
During metadata extraction (06_extract_metadata.sh), every account created by a module is
audited and classied into three categories:

 Static-Reserved: UIDs < 100 (global Debian allocations, e.g., www-data=33).

 In-Range: System UIDs landing strictly within the module's assigned window (e.g., postgres=5200
  in range 52005299).

 Out-of-Range: System UIDs allocated outside the assigned window (triggers immediate
  build failure).

   Because account creation scripts rewrite account databases whole (/etc/passwd, /etc/group,
/etc/shadow, /etc/gshadow, /etc/subuid, /etc/subgid), deltas carry full database copies.
ModFS extends reconcile.py to merge these six account databases at record granularity:

 Records are unioned by account/group name.

 Group membership lists (/etc/group and /etc/gshadow) are merged as sets rather than
  overwritten.

 Strict le permissions are enforced (/etc/shadow is preserved as mode 0640 root:shadow).

5 Semantic Record-Level Registry Reconciliation
When multiple package deltas are composed, OverlayFS by default exhibits last-writer-wins
behavior: the topmost read-only layer completely replaces underlying les at identical paths.
While this works for self-contained package binaries, it corrupts unowned system registries
global administrative les that are modied dynamically by maintainer scripts during package
installation but are owned by no individual package.
    ModFS identies eight critical system registries and categorizes them into two distinct oper-
ational models: semantic record merging and in-chroot derived state regeneration.

| UNOWNED SYSTEM REGISTRY HANDLING |

           v v

5.1 Category 1: Record-Level Merge Algorithms (reconcile.py)
reconcile.py parses registry les across all module upperdirs and writes an integrated, merged
state into the top reconciliation layer:

1. Package Status Database (/var/lib/dpkg/status): RFC-822 stanzas are parsed into
   structured dictionaries. Stanzas are unioned by Package name. For co-installed modules
   sharing identical dependencies (Class 1 benign overlap), stanzas are deduplicated.

2. Debconf Conguration Databases (/var/cache/debconf/config.dat & templates.dat):
   Stanza-formatted conguration records are unioned by record Name. The Owners eld (a
   comma-separated list of packages referencing the template) is merged as a set union. If two
   modules specify conicting values for the same debconf parameter, reconcile.py raises a
   Class 5 reconciliation error.

3. Account Databases (/etc/passwd, /etc/group, /etc/shadow, /etc/gshadow, /etc/subuid,
   /etc/subgid): Account stanzas are unioned by username/groupname. Group member lists
   are merged as set unions (e.g., preserving ssl-cert:x:115:postgres,www-data).

4. Extended Package States (/var/lib/apt/extended_states): RFC-822 stanzas tracking
   auto-installed ags are unioned. If any module explicitly requested a package (Auto-Installed:
   0), the merged record retains 0.
5. Alternatives Registry (/var/lib/dpkg/alternatives/*): Alternative groups (e.g., editor,
   awk) are parsed into priority blocks. Candidate binary paths and slave link mappings are
   unioned. Candidate priorities are preserved, and conicting priorities for the same binary
   target are resolved by taking the higher priority score.

                                               11
6. File Diversions (/var/lib/dpkg/diversions): Line-oriented diversion records added via
   dpkg-divert are unioned to preserve path redirection mappings across layers.

5.2 Category 2: Derived State Regeneration
Derived system caches are functional representations of underlying registry state. Rather than
reimplementing complex tool-specic logic in Python, ModFS regenerates derived state by exe-
cuting native system tools inside the merged chroot during composition (04_compose.sh):

 Dynamic Linker Cache (/etc/ld.so.cache): Maintainer scripts invoke ldconfig to in-
  dex shared libraries. Overlaying deltas without regenerating ld.so.cache leaves lower-layer
  libraries invisible to the dynamic linker. 04_compose.sh executes ldconfig inside the recon-
  ciled chroot, scanning all /lib and /usr/lib paths to construct a complete binary cache.

 Alternative Command Symlinks (/etc/alternatives/*): Command symlinks in /etc/alternatives/
  and /usr/bin/ point to default providers based on priority scores. 04_compose.sh executes
  update-alternatives auto <group> inside the chroot for every alternative group present
  in the reconciled registry, generating accurate system symlinks.

1 Evaluation Objectives, Framework, and Methodology
This chapter presents a comprehensive empirical evaluation of ModFS, a modular, updateable
lesystem architecture designed for Bare Metal as a Service (BAAS). The primary objective of
this evaluation is to rigorously validate the thesis claims regarding conict elimination, server-
side storage eciency, layer composition performance, and deployment reliability before host
hardware ashing.

1.1   Evaluation Objectives and Research Questions
The evaluation framework is designed to directly answer the three central Research Questions
(RQs) posed in Chapter 1:

    RQ1 (Conict Taxonomy & Reconciliation): How eectively can static metadata
     admission isolate structural conict classes, and to what extent does semantic record-level
     merging eliminate lesystem state divergence across independent module deltas?

    RQ2 (Storage Eciency): What server-side storage savings does the pinned sibling delta
     model achieve compared to traditional monolithic disk images across small adversarial,
     large realistic, and full catalogue workloads?

    RQ3 (Verication & Boot Reliability): How accurately can static metadata admission
     and structural layer verication predict the physical composability, UEFI bootability, and
     runtime service health of composed modular root lesystems?

1.2   Evaluation Methodology and Multi-Tier Validation Harness
To evaluate these questions without risking hardware ashing failures or non-deterministic test
runs, ModFS implements a stratied three-tier validation pipeline:

  1. Tier 1 (Rootless Static Metadata Admission): A lightweight, fast pre-ight check
     executing entirely in user space. It parses declarative module manifests, constructs the
     combined package dependency graph, resolves virtual package providers, and evaluates
     pairwise and triplet conict matrices against the 9-class taxonomy.

  2. Tier 2 (Physical Layer Composition and Registry Verication): An in-kernel
     physical assembly phase that mounts N read-only SquashFS module deltas alongside a
     read-write reconciliation layer using OverlayFS. Upon composition, a suite of 8 structural
     integrity assertions (V1V8) validates exact record-level database unions, symlink target
     visibility, and dpkg audit cleanliness.

  3. Tier 3 (Automated QEMU UEFI Boot Testing): An end-to-end virtualized hardware
     simulation. The composed root lesystem is attened into an ext4 disk image, booted
     inside an automated QEMU guest under UEFI rmware and systemd, and probed for
     runtime service startup, network socket bindings, and daemon health.

2 Update Strategy Costs: Intra-Generation vs. Inter-Generation
Updating software in a Bare Metal as a Service environment imposes dual overheads: server-side
storage footprint and network transfer bandwidth across ashing pipelines. ModFS evaluates
update economics under two distinct operational paradigms: Intra-Generation Specication Up-
dates and Inter-Generation Repository Upgrades.

2.1 Intra-Generation Specication Updates
An intra-generation update occurs when a systems administrator modies a module specication
(e.g., adding a package to pytools or updating conguration parameters) while keeping the
distribution snapshot pin xed (20260901T000000Z).
    Under this scenario, the modular delta structure yields massive network transfer savings.
Rather than rebuilding and re-distributing a monolithic 62.8 MB root image for webserver or a
67.6 MB image for pytools, ModFS only rebuilds and transmits the specic 21.0 MB or 25.8 MB
SquashFS delta archive.
    Across the 31-module small adversarial cohort, the average delta size is only 7.5 MB, com-
pared to an average monolithic image size of 49.2 MB. Intra-generation specication updates
achieve a 79.8% reduction in transferred bytes (1 − 7.5/49.2 = 0.7987), allowing rapid
iterative deployment over low-bandwidth management networks.

2.2 Inter-Generation Repository Upgrades and Atomic Move Mechanics
An inter-generation upgrade occurs when the infrastructure operator advances the global reposi-
tory snapshot pin (e.g., moving from Ubuntu Jammy snapshot 20260901T000000Z to 20261001T000000Z)
to ingest security patches and upstream package revisions.
    Unlike container layers that attempt dynamic cross-version rebasing, ModFS strictly enforces
an Atomic Generation Move policy:

  1. Invalidation of Cross-Snapshot Deltas: Package maintainer scripts, shared library
     symbols, and dpkg selection states evolve across snapshot dates. Stacking a module built
     against Snapshot S1 over a Base Image built against Snapshot S2 triggers a Class 2 Conict
     (Version Skew ). Tier 1 static admission checks detect snapshot mismatch in 100% of cases
     and reject the combination (REJECT).

  2. Complete Generation Re-Compilation: When the repository snapshot pin is up-
     dated, the server-side pipeline executes a full generation build: the base image is re-
     debootstrapped and upgraded against the new snapshot, and all 40 module deltas are
     re-compiled in parallel.

  3. Transfer Economics of Inter-Generation Shifts: Because dpkg maintainer scripts
     re-evaluate package state against upgraded base libraries, every delta archive undergoes
     byte-level changes. Consequently, inter-generation updates require re-shipping all mod-
     ule deltas. Space savings during inter-generation moves stem entirely from server-side
     base-sharing within the new generation, rather than incremental delta recycling across
     generations.

4.1 Server-Side Root Flattening vs. On-Node Dynamic Switching
ModFS is designed specically as a server-side build, verication, and composition frame-
work for Bare Metal as a Service.
    Server-Side Flattening: The ModFS composition engine stacks SquashFS deltas over
     the base image, executes semantic record-level registry reconciliation, and attens the
     resulting merged directory tree into a single, contiguous ext4 root lesystem image. This
     image is ashed directly onto target physical drive partitions (or served via iSCSI/NFS
     root).

    No On-Node Live Module Switching: ModFS does not run a dynamic runtime man-
     ager on physical nodes to unmount or insert module layers while the operating system is
     live. Live unmounting of lower OverlayFS layers under running processes introduces kernel
     memory page invalidations and le descriptor breakage. ModFS avoids runtime instability
     by executing all composition and reconciliation statically on the server prior to bare-metal
     deployment.

ModFS strictly enforces a Flat Sibling Delta Topology:
