# 8 Conclusion and future work

## 8.1 Answers to the research questions

ModFS investigates whether ordinary Ubuntu package installations can become independently built filesystem deltas for Bare Metal as a Service. The result is conditional: a common archive view and exact base make siblings comparable, but composition requires additional package, path, identity, registry, and runtime policies. OverlayFS captures installation changes and SquashFS stores them; neither mechanism alone establishes that the selected result is a coherent operating system. The implemented server assembles and verifies a root before flattening it into a conventional image for the node.

**RQ1 — Conflict handling.** The thesis identifies nine conflict classes and assigns each a policy. Matching package contributions can be accepted; version, declared relation, and unsanctioned ownership conflicts are rejected; upgrading the base, partitioning numeric identity allocation, and constraining directory markers prevent specific build-time failures. Shared registries require semantic reconciliation or regeneration. Runtime resource acquisition remains a separate observation. This taxonomy explains why lost package records, contradictory account identities, sibling erasure, and competing listeners cannot all be handled by one file-collision rule.

The reconciliation mechanism implements that distinction for eight registry groups: six groups are parsed and combined, while alternative symlinks and the linker cache are regenerated. The result preserves the conventional APT/dpkg layout. The demonstrated scope is narrower than arbitrary package composition: deleting siblings, full multiarch status handling, conflicting diversion arbitration, and unhandled maintainer-script state require further work. The current 40-module admission census accepted 667 of 780 pairs and 7,807 of 9,880 triples (`thesis/evidence/tier1.md`, T1.1). Its old-snapshot control exercises composability rejection, while accepted triples containing a rejected pair show why missing requirements cannot be treated as permanent pairwise exclusions.

**RQ2 — Storage.** Sharing a base reduces the modelled repository cost of retaining many variants. For the current 40-module inventory, the ratio of modelled monolithic bytes to stored base-plus-delta bytes is 1.84× overall, 5.43× for the small adversarial cohort, and 1.20× for the large cohort (`thesis/evidence/storage.md`, S1). Every headline monolithic size uses $B+d$; six actual whole-root builds calibrate that model on smaller deltas. The ratios therefore describe this catalogue and comparison model, with limited calibration of its large-payload tail. They are not measurements of per-node image size or network savings.

The historical base-fattening experiment also shows why the smallest base is not necessarily optimal for repository storage. Repeating common dependencies across many deltas can cost more than adding them to the shared base (`thesis/evidence/claims.md`, 38-module fat-base rows). The node's selected set has a different break-even condition, and ModFS's actual flattened images require their own measurements. The fleet equations in Chapter 7 express this distinction as an explicit model rather than a measured transfer result.

**RQ3 — Verification.** Static admission, physical composition, and boot observe different properties. The retained physical sweep passed its recorded checks, but predates later artefact rebuilds and verifier changes; `thesis/evidence/tier2.md` consequently withholds a current table. Its timing distinguishes composition from verification. Summing the same-sweep fits gives the historical compose-plus-verify model $336.5+72.35N$ milliseconds, excluding planning and teardown (`tier2-fit.csv`; Chapter 6). This is a descriptive fit for the retained sample, not a current portable performance guarantee.

Most retained boot bundles are also superseded. Earlier web-server boots expose runtime port contention even when package and filesystem composition succeeded. A still-current GPU-stack bundle establishes a successful guest boot without GPU access (`thesis/evidence/tier3.md`). These results show the value of execution while leaving current whole-catalogue reliability unmeasured.

Adversarial review makes the verification answer more substantial than a clean-pass claim. Counterexamples exposed checks that observed too little, evidence pipelines that mislabeled their observations, and synthetic registry-merger defects that the catalogue sweep did not reveal. `FIXED`, `CONTROL`, and `KNOWN OPEN` regressions preserve the distinctions. In particular, V7 still accepts equal-size content substitution. The contribution is a concrete account of how apparently successful verification can fail to test the property asserted about it.

## 8.2 Priorities for future work

The first priority is comparable current evidence. Metadata must satisfy the active generation schema, physical compositions must run against the exact published artefacts, and representative boots must use those same inputs. The retained evidence should identify the checker revision, metadata generation, kernel, selected set, and timing scope. This would close a freshness gap; it would not by itself expand the predicates being tested.

The second priority is stronger semantic coverage. Content checks on contested paths should test the intended winner, with explicit treatment of generated files and sanctioned replacement. Dedicated diversion and APT-mark assertions would reduce reliance on indirect checks. Multiarch package identity and deletion semantics require implementation work before widening those claims. Adversarial fixtures should accompany each new invariant, including valid controls that prevent overbroad rejection.

The third priority is controlled reproducibility and lifecycle evaluation. Independent builds need matched specifications and tools and a retained comparison of package metadata, filesystem state, and archive bytes. Generated identities and database state require a policy that preserves correct first-boot behavior. A transactional publisher, transfer client, and rollback trial must then demonstrate how complete generations reach nodes and how application data survives a return to an earlier image. Server repository savings cannot substitute for those measurements.

Hardware validation closes a separate boundary. CUDA userspace execution with an existing host driver and initialization of the packaged module without accessible hardware do not show that the packaged driver drives a GPU. That test requires the matching kernel, real hardware access, and the intended signing policy. Likewise, Ubuntu 24.04 portability results require their own published evidence rather than inheriting the Jammy evaluation.

## 8.3 Closing statement

The thesis supports modular server-side image construction within explicit compatibility boundaries. Its strongest contributions are the conflict taxonomy, the registry reconciliation mechanism, and the verification finding. Reusable filesystem bytes become a useful operating-system image only when package metadata, shared state, numeric ownership, and service behavior agree. A successful check is meaningful to the extent that its recorded predicate could have detected the relevant failure.
