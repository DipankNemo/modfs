# 5 Implementation

## 5.1 From a specification to a sibling delta

The implementation separates an operator's intent from observations of the built filesystem. `specs/modules.yaml` declares requested APT packages, module relations, a functional probe, and the conflict mechanism each catalogue member is meant to exercise. `specs/uid-ranges.yaml` assigns permanent, disjoint identity windows. The builder constructs a minimal Ubuntu base from a fixed archive snapshot and completes its upgrade against that same snapshot before building siblings. A delta build mounts the base read-only beneath an OverlayFS writable upperdir, asks APT to install the requested packages into the merged view, and compresses the upperdir as SquashFS (`docs/RUNBOOK.md`; `ARCHITECTURE.md` §§2–3, 8). Thus APT sees installed base packages, while the stored module contains only the changes it made. Whiteouts preserve file deletions. Build logs, transient caches, and build-only allocation policy are removed before compression; the allocation policy is restored to the base's bytes rather than deleted, which would create a whiteout.

Both Debian `adduser --system` and `useradd -r` can allocate identities during package installation. The builder points both at the module's assigned window *before* invoking APT; its audit then checks account records and numeric owners of files actually shipped. The permanent window prevents independent sibling builds from baking the same UID or GID into different files. The later admission check remains a guard against broken allocation or an imported artefact. The current catalogue's windows are 100 identities wide, beginning at 2000 (`thesis/evidence/catalogue.md` C1). Partitioning numbers does not combine `/etc/passwd` records; reconciliation does that separately.

Each built module has three companions: `<module>.sqsh` holds filesystem bytes, `<module>.json` is the manifest, and `<module>.files.json.zst` maps paths to owning packages and records diversions (`docs/DATA_MODEL.md`). The manifest is extracted from the **compressed artefact mounted back**, not merely from the disposable build tree. It records identity, snapshot, suite, architecture, generation, requested packages, resolved package contributions and Debian relations, module relations, removals, accounts, units, and artefact identity. This matters because excluded scratch files can appear in the build upperdir without appearing in the distributable archive. The sidecar is separate so routine metadata admission need not load every path index.

The manifest contains three digest commitments: the SquashFS artefact, the sidecar, and a named set of required manifest fields. A consumer requires the complete field set and a valid sidecar digest, then checks the digest before using path ownership. A second verification stage re-derives metadata from the artefact and compares it with the manifest. A hash inside its own document does not authenticate a maliciously replaced bundle; the mechanism detects drift and omission within the pipeline, while authenticity would require an external trust root (`docs/DATA_MODEL.md`, “The three seals”; `ARCHITECTURE.md` §5).

## 5.2 Admission, composition, and the reconciliation layer

Tier-1 admission constructs the effective package view from the base plus each module's package contribution, subtracting declared removals. It checks generation and parent identity, module `requires`/`conflicts`/`provides`, Debian `Depends`, `Pre-Depends`, `Conflicts`, `Breaks`, `Replaces`, and `Provides`, package versions, path ownership, and account identities (`ARCHITECTURE.md` §§4–5). A package manager cannot express a requirement for an entire module: a CUDA userspace module can require a driver module even when its packages were built independently. The module relation is checked on the selected set. Conversely, a rejected pair caused only by a missing provider can become admissible in a larger set, so the sampler does not treat every pair rejection as a permanent exclusion (`docs/SAMPLING_AND_BOOT.md`, Part 1).

For an admitted set, the composer mounts SquashFS artefacts read-only and builds an OverlayFS view with a writable reconciliation layer above them. OverlayFS alone chooses one entire file at a shared path. That is correct for an ordinary upper-layer replacement but wrong for state files independently rewritten by every module's maintainer scripts. The reconciler reads those registries from the participating layers, parses their records, applies registry-specific rules, and writes the combined result into the top layer (`docs/REGISTRY_FORMATS.md`; `ARCHITECTURE.md` §4). The following are the eight registry groups used in this implementation; the account and debconf groups contain several physical files.

| Registry group | Record key and operation |
|---|---|
| `/var/lib/dpkg/status` | Union installed package stanzas by package and architecture; different versions cannot be reconciled. |
| `/var/lib/dpkg/alternatives/*` | Union candidate paths and priorities within each generic-name group; reject incompatible definitions for the same candidate. |
| `/var/lib/dpkg/diversions` | Parse complete line triples and union by original path; malformed trailing records fail. |
| `/var/lib/apt/extended_states` | Union package and architecture entries; manual installation dominates automatic. |
| `/etc/passwd`, `group`, `shadow`, `gshadow`, `subuid`, `subgid` | Union names or subordinate ranges, union group member lists, and preserve sensitive modes and ownership; conflicting numeric identities fail. |
| `/var/cache/debconf/{config,templates,passwords}.dat` | Union by question name, combine `Owners` as a set, reject contradictory values, and preserve the password database's mode. |
| `/etc/alternatives/*` | Regenerate symlinks from merged alternatives candidates with `update-alternatives --auto`. |
| `/etc/ld.so.cache` | Regenerate the binary library index from the merged tree with `ldconfig`. |

The last two groups are **regenerated rather than merged**. They are functions of the composed state. A byte union of symlinks or a binary cache would not compute those functions. For a concrete case, `vim` registers `/usr/bin/vim.basic` for `editor` at priority 30, while `emacs` registers `/usr/bin/emacs` at priority 0. Taking only the highest layer's alternatives file loses one candidate; unioning candidates and rerunning `update-alternatives` retains both and selects the priority rule (`docs/REGISTRY_FORMATS.md` §2). Likewise, `postgres` and `mysql` create distinct service accounts. The uppermost `/etc/passwd` alone would lose one; the reconciler retains both records and also unions group memberships (`docs/REGISTRY_FORMATS.md` §5). The account merge is semantic: reversal of layer order produced equal record sets, but different record order and therefore different bytes (`ARCHITECTURE.md` §4).

The composer strips `trusted.overlay.opaque` from sibling deltas at squash time while retaining file whiteouts. An opaque directory created against the base can otherwise hide files introduced by an unrelated sibling, even though their paths do not collide. This was a separate failure mode from package-owned path collision (`ARCHITECTURE.md` §4). At high layer counts, relative lowerdir paths keep the OverlayFS mount option below the kernel's option-string limit (`docs/DATA_MODEL.md`, “What was hard”). These are implementation constraints, not properties implied by package metadata.

## 5.3 Verification and boot construction

The runbook orders validation as artefact-binding verification, static admission, physical composition with structural assertions, then optional boot (`docs/RUNBOOK.md`). The physical verifier checks package, alternatives, linker-cache, account, debconf, path-visibility, and `dpkg --audit` conditions against the actual layers. Each assertion is a predicate with a limited observation domain; passing it is meaningful only if the predicate models the property at issue. In particular the current visibility check compares path kind and size, leaving equal-size replacement open (see Chapter 7).

Because exhaustive physical composition grows combinatorially, `sample_sets.py` proposes admitted high-layer sets from constraints. When it can enumerate the admissible space it samples exactly; otherwise it uses a seeded, closure-aware heuristic. Every proposal still passes the authoritative tier-1 checker, and disagreements are recorded (`docs/SAMPLING_AND_BOOT.md`, Part 1). This keeps the sampler's model from silently redefining admission. It also makes a sampled sweep different from a census: its result speaks about the tested sets, not every possible set.

The boot stage composes the same filesystem, installs a snapshot-resolved kernel **into the image at packing time**, creates a GPT disk with an EFI partition and ext4 root, and boots it using QEMU with OVMF firmware. The kernel is not a sibling delta. The guest harness reports systemd state, failed units, `dpkg --audit`, module probes, and socket listeners over serial output. Each run writes an immutable bundle containing its verdict and the artefact and kernel identities; a later rebuild marks an old run superseded rather than silently reusing its verdict (`docs/SAMPLING_AND_BOOT.md`, Part 2). A driver module's userspace and kernel objects still require a compatible packing-time kernel ABI, which is checked by the recorded resolution and the guest rather than expressible as an ordinary sibling dependency (`ARCHITECTURE.md` §5).

This pipeline's operational invariant is narrow: a manifest describes the bytes actually stored, admission decides whether a selected set is allowed, reconciliation repairs known shared-state paths, and each later tier observes properties unavailable to the earlier one. The evaluation chapter reports the measurements and their generation limits.
