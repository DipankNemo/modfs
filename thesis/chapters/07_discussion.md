# 7 Discussion and limitations

## 7.1 What the verification result means

The most revealing result is about the *checks*. Across the successive adversarial reviews recorded in `JOURNAL.md`, defects repeatedly appeared in verifiers, evidence generation, and boot harnesses that accepted or reported something they had not actually observed. The review record reports no case in those passes where physical composition itself failed first and a correctly scoped checker merely needed to report it. Regression cases in `tests/` preserve `FIXED`, `CONTROL`, and `KNOWN OPEN` outcomes. They make the distinction testable: a fixed case must now fail its targeted check, a control must remain acceptable, and an open case demonstrates a known blind spot. The inconsistency audit also records 29 closed documentation findings (`thesis/evidence/inconsistencies.md`, index), though documentation findings are a different population from implementation defects and should not be summed with them.

The general pattern is visible in concrete examples. An older package-status assertion compared package names while a version mismatch could retain the same name set. A debconf merger gained a visibility exemption before there was an assertion that its records survived. A path-visibility check found absent or resized files but did not compare their content. A boot probe could report success while systemd still had a failed unit. The evidence generator could select a newer but less complete sweep and present it without the missing set size. A cost table could be labelled “compose and verify” while its column contained composition alone (`thesis/evidence/inconsistencies.md`; `tests/round2_attacks.py`; `tests/round3_evidence.py`). These are not variations of one bug. They share a methodological failure: the observed predicate was weaker than the sentence written about it.

This finding qualifies the clean structural results in Chapter 6. Passing V1–V8 on the retained sweep means the implemented predicates passed for those historical compositions. It does not establish arbitrary filesystem equivalence, byte identity, service coexistence, or correctness on rebuilt artefacts. Stronger checking would compare contested regular-file hashes, exercise the composed service configuration, and tie every verdict to the exact artefact generation. The cost of those additions belongs in the relevant tier rather than being hidden under a previously measured “verification” time.

## 7.2 Boundaries of conflict handling

Class 8 is a genuine system-level limit. Nginx and Apache can satisfy package relations and produce a structurally coherent filesystem while competing for port 80 at runtime. Which service starts first is a scheduling outcome. The retained reversed-order boot runs show nginx owning the socket and `apache2.service` failing, but most such bundles now describe superseded artefacts (`thesis/evidence/tier3.md` T3.1). This supports the existence of the conflict class, not a deterministic outcome for every boot or a current complete boot guarantee. Static declarations of well-known ports could reduce the search space; they cannot capture all dynamically chosen or externally occupied resources.

V7 has a narrower, directly demonstrated blind spot. It compares each visible path's kind and, for regular files, size. A replacement with different bytes but equal size passes. `tests/round2_attacks.py` labels this `KNOWN OPEN`, while the design discussion records a concrete equal-size executable substitution (`ARCHITECTURE.md` §3). Hashing all files in every layer would increase physical verification work; hashing contested or security-critical paths would be a narrower next experiment. Until then, “visible” must not be read as “content preserved.”

Reconciliation also supplies semantic rather than byte-level order independence. Tested reversals preserve account and debconf *record sets*, but record order and resulting bytes change (`ARCHITECTURE.md` §4; `thesis/evidence/inconsistencies.md` I-03). A different highest-layer value for a non-identity account field can still be order-sensitive. Therefore a claim that all selected modules produce one byte-identical root regardless of order is unsupported. The design permits a declared stacking priority and verifies selected semantic invariants.

## 7.3 Storage, reproducibility, and updates

The storage saving is real for the measured repository inventory but modest for its large modules and highly cohort-dependent. The 40-module comparison is 1.84×, while the small adversarial subset is 5.43× and the large subset 1.20× (`thesis/evidence/storage.md` S1). The catalogue intentionally includes conflict-provoking modules and a large CUDA outlier; its composition is part of the result. Only six monolithic roots were actually built, and those calibrate the $B+d$ model on smaller deltas. The other 34 baseline sizes are modelled, so extrapolation to the largest modules remains a threat to the exact aggregate saving (`storage.md` S2–S4). The measured saving applies to storage of many server-side variants. A node still receives a flattened, bootable image, and the evaluation does not measure a smaller per-node flash.

Snapshot pinning stabilizes *package resolution*, not every installation side effect. An independent cross-machine rebuild found differing module archives; the retained diagnostic report attributes differences to OverlayFS xattrs, generated account state, package post-install actions, ordering, and unpinned external package input (`docs/evidence/remote-verification-2026-09-20/REPORT.md`). This is evidence against a blanket byte-reproducibility claim, although the report also records toolchain and builder differences, so it is not a controlled single-variable experiment. A manifest digest binds an artefact to the bytes present at verification time; it does not make an independently rebuilt artefact share those bytes. The thesis evidence generator does not presently publish a cross-machine digest comparison table, so the numerical rebuild claim is withheld here and recorded in `NOTES.md`.

Within one generation, a module specification can be changed and that sibling rebuilt. Moving the archive pin requires a new base and siblings because the parent identity and package universe move together (`ARCHITECTURE.md` §13). The design does not yet provide transactional publication of a new catalogue or a remote transfer client. A hash change also does not imply a small byte transfer: this implementation must distribute the new artefact whole. Rollback means redeploying a retained complete image with its kernel and configuration identity; retained deltas alone do not roll back node state or application data. A fuller lifecycle evaluation needs a measured publisher, distribution path, and rollback rehearsal.

## 7.4 GPU and external validity

The GPU observations have separate scopes. The current retained local GPU-stack bundle boots and passes its guest probes without access to a GPU (`thesis/evidence/tier3.md` T3.1). Independent remote work demonstrates CUDA userspace executing on real hardware and traces runtime libraries to a rebuilt artefact (`docs/evidence/remote-verification-2026-09-20/REPORT.md`). A separate project record reports a GTX 1060 userspace run (`JOURNAL.md`, 2026-09-21); these are distinct experiments and should not be collapsed into one machine or driver claim. The ModFS NVIDIA kernel module was shown to load, link, and initialize in its target kernel, but the reported run stopped at hardware enumeration; it has not driven a passed-through GPU. Userspace execution with a provider's existing driver does not validate the packaged driver on that hardware. Kernel ABI compatibility, unsigned module policy, and Secure Boot remain deployment boundaries (`ARCHITECTURE.md` §§5, 9).

The work demonstrates a coherent method for a pinned APT/dpkg generation on the measured Ubuntu catalogue. It does not establish representativeness across distributions, long-lived node mutation, production port-allocation policy, or arbitrary kernel-driver combinations. The immediate research priority is to rerun physical verification and representative boots after the last artefact rebuild, then strengthen assertions against same-size substitution and report each result with its exact catalogue and generation. The larger lesson is that a verifier should be evaluated as an instrument: every acceptance claim needs a counterexample that would make its own checker refuse it.
